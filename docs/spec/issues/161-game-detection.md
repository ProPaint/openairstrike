# 161: choosing the game and finding its data (A4)

One binary runs three games (`as3d`, `as2`, `gulf`); this is how it finds out which one and
where its files are. Code: `engine/include/as3d/game_data.h`, `engine/src/game/game_data.cpp`.

## Layout under the data root

| Game | Install (exe, `data/pak*.apk`, `data/Settings.xml`) | Extracted files |
|---|---|---|
| `as3d` | `third_party_local/original/` | `assets_extracted/` |
| `as2`, `gulf` | `third_party_local/games/<key>/` | `assets_extracted_games/<key>/` |

`locateGameData(root, game)` applies it: paks in the profile's mount order (only those that
exist; the rest are listed in `missing`), `Settings.xml`, the logo `data/gfx/logo2s.tga`, the
profile's texts file in the extracted directory. `detectGames(root)` lists the games that have
data, in the order as3d, as2, gulf.

## Identifying paks

Since issue 170 a pak is identified by the names in its file table, not by its bytes, so that
any build of a game is accepted. `identifyPakFile(path)` (`as3d/game_data.h`):

1. The fast path: `pak0.apk`'s size and the FNV-1a 64 hash of its first 64 KB against the
   three signatures of the builds the specs came from (below).
2. The file table (`as3d/pak_file.h`, `readPakTable`: the header and the XORed table, not the
   bodies). A table or a body that ends past the end of the file is a truncated pak, refused
   with the number of bytes missing (a split CAB leaves such files).
3. The entry names, ASCII lower-cased with `\`, sorted: their count and the SHA-256 of their
   LF-joined list are compared with the fingerprints of the owner's paks compiled into
   `game_data.cpp` (`kPakFingerprints`, one per pak of every game, generated by
   `tools/paktool.py fingerprint` from `tools/pak_entries/<key>[.pakN].txt`): an exact match
   names the game and the pak. The sequels' `pak2.apk` share their names (the music): alone it
   is ambiguous, beside a pak0 it is that game's.
4. No exact match: the best Jaccard overlap with the lists themselves, when the engine has
   them (`$AS3D_PAK_ENTRIES`, the source tree's `tools/pak_entries/` on the desktop, the APK's
   `assets/pak_entries/` for the Android import). A `pak0.apk` is a game's at 0.98 or more
   (`identifyPak0File`), another pak beside an identified pak0 at 0.9 (`pakMatches`); an
   override pak the profile lists without a reference (AirStrike 3D's `pak3.apk`) when all its
   names are the game's (`shareOfGameNames`). Without the lists only the exact matches work.

Names and paths are still not trusted (a directory called `gulf` holding the first game's
paks is the first game). The full SHA-256 of every known build of every pak is in
`tools/games.json` (`pak_sha256`, a list per name) for the tools, the web page and the
importer's fast path.

| Game | pak0.apk size | FNV-1a 64 of the first 64 KB | entries | names SHA-256 (first 12) |
|---|---|---|---|---|
| as3d | 16717041 | `4fe87f398b954b0a` | 1201 | `a136df9f0e86` |
| as2 | 39411244 | `095dd5524bc31d6f` | 1609 | `3e0dd60f0cc6` |
| gulf | 35840140 | `bf1903a53496c57e` | 1142 | `8eb8c2663109` |

`detectGames` only accepts paks under a game's own install directory when they identify as that
game.

## A copy without pak0.apk

Some downloads keep `pak0.apk`'s content as loose files under `data/` (`gfx/`, `models/`,
`textures/`, ...). `chooseGameData` with `--paks DIR` and no `DIR/pak0.apk` lists the files
under DIR (`looseFilesUnder`), takes the game whose pak0 names they cover by 99 % or more
(`gameOfLooseFiles`; `--game` restricts it) and writes a `pak0.apk` from them
(`writePak0FromLooseFiles`: stored bodies, zero key, the reference order) under
`root/third_party_local/built/<key>/`, or into DIR when the root cannot be written; the log
says where, and the next run reuses it when it still identifies as the game. The importer does
the same for a game directory without pak0, loose or in a zip.

## Choosing

Desktop tools (`as3d_game`, `as3d_sim`, `as3d_viewer`, `rcsl_tool`): `--game KEY`, else
`$AS3D_GAME`, else `as3d` if present, else the first detected game. `--paks DIR` without a key
identifies the game from the paks. An unknown key, a game without data or paks that match no
game is an error that lists the detected games (`chooseGameData`). `--list-games` prints key,
title, version and where each game was found. `--data ROOT` and `$AS3D_DATA_ROOT` name the root.

Mounting (`GameSession`): the game's extracted directory, or, with `GameOptions::paks`, the
paks in the profile's order (Gulf Thunder's `pak4.apk` last, so it overrides); the extra files
(Settings.xml logo) go underneath as before. The desktop tools mount the extracted directory
unless `--paks` is given or the game has none. A pak the profile marks optional
(`GameProfile::optionalPaks`: AirStrike 3D's `pak3.apk`) is skipped when it is not there; the
hosts list the profile's paks without looking, `mountGameFiles` closes the gap.

Android and web: the game is `--game KEY` (intent extra `game`, URL parameter `?game=`),
default `as3d`. A game that is not `gameIsPlayable` is refused with a log line ("not playable
yet") unless `--allow-unfinished` (extra `allow_unfinished`) / `--unfinished` (`?unfinished=1`)
is given. Turning the intent extras into arguments is in `GameActivity.getArguments()`.
